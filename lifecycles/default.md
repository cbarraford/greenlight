# Default MR lifecycle

Used for any repo without its own `lifecycles/<repo>.md`. Same as `examples/lifecycles/release-train.md`, minus the review bot and the milestone. Put your own in `~/.greenlight/lifecycles/<repo>.md`.

1. `mr_open` — An MR exists for the branch. Owner: agent. Implement the goal, run `python3 ~/.claude/skills/greenlight/scripts/greenlight.py scan`, then `python3 ~/.claude/skills/greenlight/scripts/audit.py gate push --execute` from the clean worktree to audit and push the exact commit (add `--target <base branch>` when the PR will target a nondefault branch). Put the draft MR's exact title and body in a JSON file outside the worktree as `{ "title": "...", "body": "...", "target": "<base branch>" }`, then run `python3 ~/.claude/skills/greenlight/scripts/audit.py gate pr <metadata.json> --execute` to audit and create the draft. Use the push gate for later agent pushes.
2. `ci_green` — The head pipeline succeeded (or there's no CI). Owner: CI while it's running; agent when it failed.
3. `no_conflicts` — No merge conflicts. Owner: agent (rebase).
4. `ready` — Not a draft. Owner: greenlight, unless the goal says to keep it as a draft. Then ask the user.
5. `threads` — No unresolved threads. Owner: agent (verify, then fix or reply, and resolve).
6. `approved` — The required approvals are in. Owner: reviewers.
7. `merge` — The forge reports it mergeable. Owner: greenlight merges automatically.

GitHub PRs follow the same steps: greenlight maps the PR onto the MR shape (checks → pipeline, review threads → threads, `mergeStateStatus` → merge status) and runs `gh pr ready` / `gh pr merge` itself (`merge_method` in config.json picks merge, squash or rebase).

A lifecycle can add an `Options:` line of backticked flags:
- `solo`: nobody else reviews this repo. A mergeable MR/PR with no other human's approval goes to the user ("review it, then merge?") with the merge command attached, instead of waiting on reviewers.
- `automerge`: the lifecycle's own steps stand in for a human approval. A mergeable MR/PR whose every earlier step passed is merged by greenlight without waiting on reviewers or asking the user (a goal that says "hold" still asks). It needs at least one of your own steps before `merge` that checks the work (an agent's independent reviews, a try-out, each `Done: `label=…``); a lifecycle with none never automerges.
- `merge_any_base`: greenlight may merge an MR/PR whose target isn't the default branch. Without it a stacked GitHub PR waits on the PR its base branch comes from (`dependency`), or asks the user when there is none.
- `merge_method=merge|squash|rebase`: overrides global `merge_method` from config.json for this repository.
- `review_bot=<username|none>`: overrides global `review_bot` from config.json for this repository (`none` disables it).
- `human_approval=true|false` (or `no_human_approval`): overrides global `require_human_approval` for this repository. With `require_human_approval: true` and no per-repo override, a repo whose forge requires no approvals asks you to merge ("mergeable, nothing blocks it: merge it?") instead of waiting on reviewers; `human_approval=true` waits for another human's approval anyway.
- `auto_rebase`: dispatch an agent to rebase when the forge reports `need_rebase` (no conflicts), instead of asking the user.
- `milestone=<prefix>`: prefix for the active release milestone step (default `Release-`).
- `host=server|mac|auto`: where Chief and agents run for this repository (default `server`; `mac` runs on your Mac for local apps, Xcode, or GUI tests; `auto` picks the Mac when those markers are present).

A step that isn't one of the built-ins above is your own: ``N. `qa` — QA passed. Done: `label=qa-ok` `` passes once the MR has that label, ``Done: `check=e2e` `` passes once that CI check succeeds, and ``Done: `signoff` `` asks you once per MR (with optional ``Run: `cmd` `` to run a command first). Any custom step may also set ``Owner: `agent|me|reviewers|ci` `` and ``Phase: `define|build|verify|review|land` ``. Steps before `mr_open` run before an MR is opened (keyed per branch); steps after `merge` run once it lands (deploy, verify) and cleanup keeps the workspace until they're done. `mr_open` is the implement phase: the goal is being built until the MR exists.

**Semantic audit.** Before anything an agent did unattended leaves the box, `scripts/audit.py` asks System One (`scripts/decide.py`) four contracts in parallel (one `decide.batch`), each phrased so yes means kept:

| check | contract | asks |
|---|---|---|
| `diff_matches_goal` | NoScopeCreep | every change in the diff serves the goal |
| `tests_not_weakened` | GenuineFix | no test was deleted, skipped or loosened so the change passes (it's shown the asserts removed and skips added) |
| `thread_truly_addressed` | NoBrushOff | each reply fixes the reviewer's point or gives a checkable reason, not a thank-you or a promise |
| `no_secrets_or_pii` | SafeToPublish | nothing outbound (the diff's added lines, a comment, `report.html`) carries a credential or personal data |

A contract fails when the model puts its chance of holding at or below 1 − `audit.threshold` (config.json `"audit": {"threshold": 0.8, "post": 0.75, "draft": 0.45, "require_model": true}`). A diff too long for one question is asked in parts, and every part must pass. An answer from decide's local fallback (no model set up) is a guess and never fails a contract by itself, but the audit is held until every contract has a real model answer by default. SafeToPublish also scans for credential and recognizable personal-data shapes in added content, destination filenames, commit messages and outgoing comments; a hit always fails (except exact known credential examples and email addresses at IANA-reserved `example.com`, `example.net`, or `example.org`). Model-bound context masks private values before asking. An unverified answer is re-audited after 10 minutes. An audit that can't run (no diff, an empty diff, decide erroring) fails too.
- Auto-run (Settings › Repositories): a run whose gate lets it push is told to commit its changes, then run `audit.py gate push --execute`, which audits and pushes that exact commit to the MR source branch (optionally `--force-with-lease`). A `BLOCKED` line stops it. Before the MR exists, the gate uses the scanned worktree branch. A run whose gate lets it post (`Push, post & resolve`, `Post comments`) writes its comments to a file and runs `audit.py gate post <file> --kind reply --execute` for replies or `--kind review --execute` for review comments: the **outbound scorer** rates each for severity, evidence and non-nitpickiness (a reply: NoBrushOff and its evidence). Each reply supplies a live `thread_id`; the gate fetches the discussion and scores its real text. Only high-precision ones (mean ≥ `post`, every score and contract answer from a real model; review severity ≥ 0.5, evidence ≥ 0.75, and non-nitpick ≥ 0.75; replies also need a NoBrushOff probability ≥ `post`) are posted (the gate posts approved review comments and posts/resolves approved replies itself). Medium ones (≥ `draft`) stay in the run's last message as local drafts, and weak nits are dropped. A comment that fails SafeToPublish is never posted; its content is redacted from gate output.
- Every unattended Greenlight merge: the exact local source and target commits are checked against the forge, then their full text diff (including binary payloads, with diff drivers off) and commit messages are audited in the background (`audit.py merge <worktree>`, cached per head under `~/.greenlight/audit/`). A cached pass is reused only while the target commit stays the same. Until it answers, the step reads "automerge waits on the semantic audit". Immediately before merging, the command checks the target branch and commit again and pins the audited head (`--match-head-commit` / `--sha`). A failed contract holds the merge and asks you, naming the contract ("automerge held by the semantic audit: GenuineFix (tests_not_weakened, p=0.93)"). Your own Merge click is never gated.
- `audit.py publish <file>` runs SafeToPublish on a file before it's shared (the report).

If `gate post --kind reply --execute` reports an uncertain reply, inspect the live forge discussion before retrying. The gate leaves a local `.pending` marker to block duplicate posting. Only when no reply was posted, remove the marker named in the error and rerun the gate; if the reply exists, resolve that discussion manually and keep the record.

When a step is on you (or it's an agent's step and no agent is on it), the workspace's card recommends what to do next. The built-in steps have written-out advice; for your own steps the model writes one line alongside the next-step prompt. Click the card's steps bar to see the whole lifecycle as a checklist. A `## Rules` section at the end holds standing requirements every agent on the repo is told to follow. The app's Settings → Repositories edits all of this.
